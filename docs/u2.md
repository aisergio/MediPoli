## Resumen

MediPoli es una IPS ficticia de Bogotá que presta servicios de medicina general y odontología a afiliados simulados del régimen contributivo de SaludCol. El proyecto diseña un portal que centraliza la agenda de tres sedes y protege la reserva de un mismo horario cuando llegan solicitudes concurrentes. La demostración trabaja con quince profesionales y sesenta pacientes ficticios.

La entrega define los actores, las reglas de reserva y la arquitectura de destino. Terraform modela la red, el estado remoto, el almacenamiento y el laboratorio que permite comprobar el trayecto desde el balanceador hasta una lectura de DynamoDB. El portal y la auditoría por eventos se incorporan en U3. El despliegue gradual y su recuperación se verifican en U4.

# Contexto del caso

La IPS ficticia opera tres sedes en Bogotá. Cada sede tiene cinco profesionales empleados. La agenda se prepara con veinte pacientes de prueba por sede y franjas de treinta minutos. Estas cantidades delimitan la demostración y permiten repetir las pruebas con el mismo catálogo.

Cuando las sedes gestionan horarios en registros separados, el paciente necesita consultar disponibilidad por varios canales y el personal debe reconciliar cambios manualmente. Una reserva concurrente puede producir dos confirmaciones para el mismo horario si la validación se realiza solo en pantalla. El objetivo es que cada franja tenga como máximo una cita confirmada y que la agenda cambie de forma consistente cuando se cancele o reprograme.

# Alcance funcional y reglas de reserva

El paciente se autentica antes de consultar sus citas o cambiar su estado. La búsqueda filtra por servicio, fecha y sede. La reserva se confirma al guardar. El pago es presencial y queda fuera de la aplicación. La demostración excluye historias clínicas, facturación electrónica, verificación real de afiliación, exportación de reportes y edición avanzada de agendas.

![Casos de uso del paciente, profesional y administrador](02-casos)

Figura 2. Capacidades por actor. Las dos reglas unidas a la reserva se verifican antes de confirmar la transacción.

# Requisitos no funcionales

Los objetivos se miden en la ventana de demostración y con datos ficticios. Para cada prueba se conservarán el ambiente, volumen, fecha, versión y resultado.

| Requisito | Criterio | Verificación |
| --- | --- | --- |
| Rendimiento MP-11 | p95 de disponibilidad ≤ 2 s con cinco usuarios simultáneos | P-11 registra muestra, p95, p99, 5xx y arranques en frío por separado |
| Disponibilidad MP-12 | Medir las operaciones correctas durante la ventana de prueba | P-12 observa el efecto de una versión defectuosa y verifica el regreso a la estable |
| Seguridad MP-02 y MP-07 | Acceso a información propia y funciones administrativas por rol | P-02 comprueba identidad. P-07 intenta lecturas con otro usuario de prueba |
| Privacidad MP-07 y MP-09 | Datos sintéticos y registros sin credenciales ni información clínica | Revisar salida, eventos, consola y repositorio antes de publicar |
| Reproducibilidad MP-10 | Repetir el plan sin cambios con la misma entrada | P-10 compara el plan con el estado después de aplicar |
| Accesibilidad MP-13 | Flujo utilizable con teclado y a anchos móvil y escritorio | Revisar foco, etiquetas, mensajes de error y contraste |

El p95 es el valor que cubre el 95 % de las mediciones ordenadas. La aceptación de la consulta se orienta al p95, mientras que el p99 describe la cola de latencia. En muestras pequeñas se informará el tamaño para evitar conclusiones de disponibilidad a escala real.

La prueba de competencia por una franja tiene un objetivo diferente de la prueba de carga. Dos pacientes se autentican y solicitan el mismo horario. Solo una respuesta puede confirmar la cita. La otra debe informar el conflicto sin cambiar el cupo del paciente. Ambos resultados se comprueban consultando el estado final.

El registro de la reserva utiliza UTC para ordenar y validar fechas, y muestra horas locales de Bogotá en la interfaz. Esto evita que el navegador altere el significado de una cita al cambiar la zona horaria del dispositivo.

# Componentes de la arquitectura

La aplicación adopta servicios administrados de AWS. El portal se genera como archivos estáticos y los cambios de citas se validan en el servidor. Las lecturas de agenda y los cambios de estado usan la misma API, mientras que la auditoría procesa cambios de forma asíncrona.

![Arquitectura de destino de MediPoli](03-componentes)

Figura 3. Arquitectura objetivo de U3. Las flechas continuas representan solicitudes o eventos. Las discontinuas representan registros y métricas.

Cloudflare dirige las rutas del proyecto a CloudFront. La distribución entrega el portal desde un bucket privado mediante control de acceso al origen. El comportamiento de API y MCP reenvía la autorización y deshabilita la caché. Cognito autentica identidades y API Gateway limita tráfico y verifica los tokens de la web. Lambda valida el rol y las reglas de reserva.

DynamoDB conserva las citas, el estado de las franjas y los cupos por servicio. Streams representa la modificación persistida y permite que un segundo ejecutor escriba auditoría de forma independiente. La confirmación al paciente se basa en el resultado de la transacción. La auditoría puede recuperarse sin repetir esa reserva.

En dev, Terraform define la VPC 10.30.0.0/16. Dos subredes públicas tienen una ruta hacia Internet Gateway. Las dos privadas reciben las rutas administradas de S3 y DynamoDB y carecen de ruta por defecto. El entorno prod emplea 10.40.0.0/16 y su propio estado.

![Trayecto de la prueba de red U2 y las subredes por zona](04-red)

Una petición GET al balanceador con origen IPv4 autorizado llega a una función que consulta únicamente LAB#STATUS. La función responde con el ID de solicitud y el resultado de la lectura. El laboratorio mantiene su estado separado y retira el ALB, la función de prueba y el registro sintético después de comprobar el resultado. La configuración de destino usa API Gateway como entrada pública y mantiene la red privada que necesita el consumidor de eventos.

# Modelo de datos y concurrencia

El modelo distingue la franja disponible de la cita registrada. Una franja pertenece a un profesional, una sede, un servicio y un instante. Un historial puede incluir una cita cancelada y una cita posterior sobre la misma franja. Solo la cita activa ocupa el horario.

![Entidades que intervienen en la disponibilidad y la cita](05-datos)

Figura 5. Modelo lógico. CupoServicio identifica el par paciente y servicio que se protege entre sedes. La auditoría conserva eventos por revisión.

La transacción de reserva cambia la franja de disponible a ocupada, crea la cita y actualiza el cupo del paciente. Las condiciones verifican que la franja siga disponible y que el cupo previo haya vencido o esté libre. Si dos solicitudes compiten por cualquiera de los elementos, solo una cumple las condiciones.

La cancelación libera la franja y el cupo de la cita propia. La reprogramación reserva la nueva franja, actualiza la cita y libera la anterior en una sola operación. Una clave de idempotencia permite responder al reintento de una misma solicitud sin crear otra cita.

# Identidad y autorización

La autenticación usa cuentas ficticias de Cognito y un flujo OAuth con PKCE. El portal estático inicia el acceso y envía un token a la API. El servidor deriva la identidad del paciente del sujeto validado y aplica el rol antes de leer o modificar citas. El identificador recibido en una URL, en un formulario o en una llamada MCP nunca sustituye la identidad autenticada.

| Actor | Acciones permitidas | Verificación negativa |
| --- | --- | --- |
| Paciente | Consultar disponibilidad y gestionar citas propias | Pedir la cita de otro paciente de prueba |
| Profesional | Consultar su agenda | Solicitar una agenda ajena o intentar registrar citas |
| Administrador | Altas de demostración y conteos | Verificar que un paciente recibe 403 en administración |
| Cliente MCP | Disponibilidad, consulta propia y reserva confirmada | Probar token ausente, audiencia incorrecta y reintento |

La configuración de CloudFront separa activos estáticos de rutas autorizadas. Los activos del portal pueden reutilizarse en caché. Las respuestas de agenda se solicitan sin caché y se devuelven al usuario que las pidió. El bucket bloquea acceso público.

La aplicación se presenta como proyecto académico y no solicita datos reales de afiliación. Las cuentas de demostración se generan con direcciones de prueba y las contraseñas se mantienen fuera del historial de Git. Los registros incluyen operación, duración, resultado e identificador de correlación.

La autenticación del MCP se prueba con un cliente que pueda completar OAuth y ejecutar herramientas. Si ChatGPT limita la escritura, la demostración del servidor se resuelve con un cliente compatible. El resultado del ensayo queda identificado por cliente.

# Gobierno, permisos y secretos

La cuenta del proyecto aísla los recursos y el coste de MediPoli. Los archivos de Terraform incluyen la cuenta esperada en la configuración del proveedor para impedir aplicaciones accidentales en otra cuenta. El estado y los planes se mantienen privados por la posibilidad de contener valores provistos a los recursos.

| Identidad | Alcance | Control |
| --- | --- | --- |
| Operador de infraestructura | Aprovisionar red, estado y recursos iniciales | Perfil temporal y cuenta esperada antes de planificar y aplicar |
| Función de laboratorio | Leer LAB#STATUS y escribir sus logs | Tabla y clave limitadas por política. Entrada solo desde el grupo de destino |
| Función de agenda | Operaciones de agenda y altas en el pool asignado | Recursos del ambiente, permisos del rol y verificación del usuario |
| Consumidor de eventos | Leer el stream y escribir auditoría y fallos | Identidad dedicada y registros con retención definida |
| Release en GitHub | Actualizar código y publicar archivos del ambiente | Credenciales efímeras, audiencia STS y sujeto OIDC exacto |

La creación de interfaces elásticas de red para Lambda requiere permisos de EC2 administrados por el servicio. Se incluyen únicamente las operaciones necesarias para sostener el vínculo con las subredes. La autorización del balanceador para invocar la función se restringe a su grupo de destino.

U2 conserva el plan Free y las funciones avanzadas desactivadas. El presupuesto mensual se administra en AWS Budgets. Las alertas se dirigen a un correo que se mantiene fuera del repositorio y de las evidencias públicas.

Para controlar drift se revisa el plan antes de aplicar y se ejecuta después un segundo plan con las mismas entradas. Una diferencia en recursos administrados requiere identificar el cambio y su propietario antes de corregirla.

# Estructura y estado de Terraform

El repositorio distingue configuración base, módulos reutilizables y laboratorio. Un mismo conjunto de módulos se instancia con parámetros distintos en dev y prod.

| Ubicación | Propósito | Estado |
| --- | --- | --- |
| infra/bootstrap | Crear bucket de estado protegido con cifrado y versión | Local, privado y separado |
| infra/ambiente | Instanciar red, datos y controles por ambiente | S3 con dev/base.tfstate o prod/base.tfstate |
| infra/modulos/red | VPC, subredes, tablas de ruta y endpoints | Administrado desde el ambiente |
| infra/modulos/datos | Agenda y auditoría con recuperación en el tiempo | Administrado desde el ambiente |
| infra/laboratorio | Prueba temporal ALB, Lambda y lectura sintética | S3 con dev/laboratorio.tfstate |

El bucket de bootstrap bloquea acceso público, cifra el almacenamiento y conserva versiones. Terraform utiliza un archivo de bloqueo S3 para serializar operaciones sobre el mismo estado (HashiCorp, s. f.). El estado del laboratorio se retira de la ejecución sin volver a crear la red ni afectar el catálogo del ambiente.

El archivo de variables distingue el ambiente y la activación de la aplicación. La red usa las primeras dos zonas disponibles de la región asignada. El identificador de la cuenta se valida como dato de entrada y restringe el proveedor. El despliegue de U2 se limita a la base dev y al laboratorio temporal.

La evidencia de idempotencia es el segundo plan con código de retorno 0. La validación de sintaxis y esquemas puede ejecutarse antes de acceder al proyecto. Cada comprobación responde una pregunta distinta y se registra por separado.

# Fragmentos de la infraestructura

La función de laboratorio se ubica en subredes privadas. Su ruta de datos llega a DynamoDB mediante un endpoint gateway. Este fragmento muestra cómo se conecta el endpoint a la tabla de rutas privada.

```hcl
# El servicio se selecciona por región y se asocia a la ruta privada.
resource "aws_vpc_endpoint" "gateway" {
  for_each          = toset(["s3", "dynamodb"])
  vpc_id            = aws_vpc.main.id
  vpc_endpoint_type = "Gateway"
  service_name      = "com.amazonaws.${var.region}.${each.value}"
  route_table_ids   = [aws_route_table.private.id]
}
```

La configuración del backend distingue el cifrado del bloqueo de operaciones. Bucket, región y clave se proporcionan al inicializar el ambiente. Las credenciales se resuelven fuera del archivo.

```hcl
terraform {
  backend "s3" {
    encrypt      = true
    use_lockfile = true
  }
}
```

La condición LeadingKeys del rol de laboratorio permite GetItem sobre un único dato de demostración en la tabla. El código de la función solicita esa clave con lectura consistente y devuelve HTTP 200 si coincide el valor esperado. El resultado HTTP y el registro asociado constituyen la evidencia del trayecto.

Los fragmentos proceden de los directorios infra/modulos/red, infra/ambiente e infra/laboratorio del repositorio. El formato y la validación se aplican al código íntegro, no al recorte incluido aquí.

# Flujo de automatización

La rama de trabajo contiene una unidad de cambio. El pull request reúne requisitos asociados, diferencias del código, comprobaciones y decisiones de revisión. Antes de pasar a main, la validación de Terraform inicializa los proveedores sin backend y comprueba formato y esquemas.

![Validación y aplicación desde una rama y un pull request](06-pipeline)

Figura 6. Flujo por ambientes. En U2 se verifican los pasos locales y la validación inicial. U4 incorpora el release progresivo con control de tráfico.

El plan de infraestructura consulta el estado privado y debe corresponder al commit revisado. El operador aplica ese plan, captura el resumen y comprueba convergencia con un segundo plan. Los resultados se conservan como extractos saneados.

GitHub Actions obtiene credenciales temporales con OIDC para los despliegues de aplicación. La confianza se limita al sujeto exacto del repositorio y del ambiente. Al definir el sujeto se verifica el formato que usa el repositorio, incluidos identificadores inmutables cuando corresponda (GitHub, s. f.). La validación de pull requests utiliza permisos de lectura.

La promoción a prod exige una acción explícita del ambiente. U4 observa una versión candidata durante el Canary y devuelve el tráfico a la versión estable cuando las pruebas fallan.

# Estimación de costes

La estimación modela un ambiente académico activo con 76 usuarios ficticios, 10.000 peticiones HTTP mensuales y 20.000 invocaciones de Lambda, incluidas las de auditoría. Los importes están en USD y excluyen créditos promocionales e impuestos. Se aplican las cuotas sin coste de Cognito y CloudFront cuando están disponibles. Se redondean los demás importes hacia arriba para facilitar la comprobación (Amazon Web Services, s. f.-g, s. f.-h, s. f.-i, s. f.-j, s. f.-k, s. f.-l).

| Servicio | Supuesto mensual por ambiente | USD aproximados |
| --- | --- | --- |
| API Gateway HTTP | 10.000 solicitudes a USD 1 por millón | 0,01 |
| Lambda | 20.000 invocaciones de 256 MiB y 0,25 s; incluye invocaciones y 1.250 GB-s | 0,03 |
| DynamoDB | 1 GB de datos y recuperación puntual. 40.000 unidades de lectura y 10.000 de escritura | 0,47 |
| S3 | 2 GB-mes con versiones, 10.000 GET y 1.000 PUT | 0,06 |
| CloudWatch | 0,5 GB de registros, tres alarmas estándar y un panel | 3,57 |
| Cognito y CloudFront | 76 usuarios directos en Cognito Essentials. CDN con 50.000 solicitudes y 5 GB de salida | 0,00 |
| Total de planificación | Consumo de referencia por ambiente con las condiciones anteriores | 4,14 |

Con dos ambientes comparables, el escenario suma unos USD 8,28 al mes. El total es una estimación de operación y se contrasta con el consumo del proyecto durante U3. Exceder el volumen o la cuota compartida cambia el cálculo. Los endpoints gateway de S3 y DynamoDB carecen de coste adicional (Amazon Web Services, s. f.-d).

| Control | Configuración |
| --- | --- |
| Alertas de consumo | Budget mensual por USD 50. Avisos de coste real al superar USD 30, USD 40 y USD 50 |
| Pausa del proyecto | Free vigente en U2. Un límite monetario a USD 50 requiere Paid y se gestiona en AWS Settings |
| Base de medición | Coste real observado en AWS Budgets. La proyección de la arquitectura se calcula antes de créditos e impuestos |
| Control operativo | Sin NAT permanente, registros de retención limitada y retirada del balanceador de prueba |

Budget avisa del coste observado y los datos de facturación pueden llegar con retraso. En U2 se conservaron notificaciones por correo. La suspensión integral por importe mensual es una capacidad del límite nativo de Paid (Amazon Web Services, s. f.-a, s. f.-b).

Un ALB a USD 0,0225 por hora y dos IPv4 públicas a USD 0,005 cada una suman USD 0,13 de coste fijo estimado durante cuatro horas. A ese subtotal se añade el consumo de LCU. Mantenerlo 730 horas elevaría el mismo componente fijo a unos USD 23,73. Por eso el balanceador de U2 es temporal y la arquitectura de agenda usa una API HTTP bajo demanda (Amazon Web Services, 2024, s. f.-m).

Terraform CLI se usa localmente. El repositorio público utiliza ejecutores estándar. Cloudflare se mantiene en su cuota gratuita, Mermaid.ai se usa con la suscripción existente y los videos opcionales se renderizan localmente con HyperFrames. Los cargos de esos servicios se consideran fuera del presupuesto de AWS.

# Decisiones y riesgos técnicos

| Alternativa de entrega | Efecto en la operación |
| --- | --- |
| GitHub Actions con OIDC y Terraform | Una sola entrada desde GitHub y credenciales temporales. Requiere probar la confianza por ambiente |
| GitHub Actions más CodePipeline y CodeBuild | Evidencia dentro de AWS y roles de servicio. Añade recursos y una integración que administrar |
| GitHub Actions más HCP Terraform | Separa el entorno de ejecución de infraestructura. Añade coordinación con otra plataforma |

Se adopta GitHub Actions con OIDC porque el trabajo es individual y los cambios y validaciones ya se revisan en el repositorio. Se mantiene Terraform para infraestructura y se separa el control del tráfico de las versiones de Lambda. Esa división permite revertir la aplicación sin restablecer el estado de datos.

Una aplicación tradicional siempre activa tras un balanceador simplifica algunos flujos de red, pero exige operar instancias y ajustar capacidad incluso con tráfico irregular. Lambda y API Gateway reducen esa carga a cambio de arranque en frío y límites del servicio. Se documentarán los tiempos con y sin arranque en frío durante U3.

La dependencia de DynamoDB se concentra en transacciones, índices y eventos. El coste de cambiar de almacenamiento incluye reproducir garantías de concurrencia y deduplicación. La alternativa de una cola adicional se considerará solo si la auditoría necesita varias aplicaciones consumidoras o si cambia la retención requerida.

El mayor riesgo funcional es confiar en el estado de la interfaz para conceder la franja. La transacción y la prueba concurrente son los controles de aceptación. El mayor riesgo operativo es el gasto persistente de recursos temporales. La ventana de laboratorio y la comprobación de retirada dejan una evidencia para ese riesgo.
